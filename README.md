# Requirements Analysis

**ID:** RA-PRODUCT-BFE-DRIVE
**Статус:** ""

## Видение системы — VISION-BFE-DRIVE

Облачное файловое хранилище по принципу OneDrive, в котором пользователи могут хранить файлы и папки, управлять файловой структурой, получать назначенный администратором доступ к отдельным папкам файлового дерева и в дальнейшем работать с хранилищем через Web, Desktop и Android-клиенты.

## Цель проекта — GOAL-BACKEND-V1

Создать законченное серверное ядро облачного файлового хранилища и стабильный API-контракт, достаточный для последующего независимого подключения Web, Desktop и Android-клиентов. Сервер должен обеспечивать аутентификацию пользователей, файловое дерево, хранение содержимого файлов в Yandex Object Storage, управление доступом к папкам, журнал изменений и протокол инкрементальной синхронизации, а также обнаружение конфликтующих изменений по версии файла. Клиентские приложения в данный проект не входят.

# Границы Backend V1 — SCOPE-BACKEND-V1

## Входит в Backend V1

### SCOPE-ADMINISTRATION

Администратор системы имеет глобальный доступ ко всем файлам и папкам системы. Администратор может выполнять над любыми файлами и папками все файловые операции, предусмотренные для аутентифицированного пользователя, включая просмотр структуры и содержимого, получение исходного файла, создание папок, загрузку файлов, изменение содержимого, переименование, перемещение и удаление. Ограничения ACL и скрытия родительской структуры не ограничивают эти административные полномочия.

Административные учётные записи после первоначальной инициализации управляются отдельно от обычного создания пользователей.

Выбрана следующая модель:

```text
ADMIN
→ создаёт обычную non-admin учётную запись
→ задаёт initial login + password
→ отдельной операцией предоставляет global administrative powers
→ учётная запись становится ADMIN
```

`BP-ADMIN-CREATE-USER` всегда создаёт только **non-admin** учётную запись. Он никогда не создаёт ADMIN неявно.

При создании учётной записи ADMIN задаёт первоначальные credentials:

```text
initial login
+
initial password
→ достаточны для последующей authentication
```

Login должен быть допустим и не конфликтовать с существующей учётной записью, password должен быть допустим. Конкретные правила допустимости и техническая проверка credentials на уровне `RequirementsAnalysis` не определяются.

После появления первоначального администратора предоставить глобальные административные полномочия существующей non-admin учётной записи может только уже существующий аутентифицированный ADMIN.

```text
NON-ADMIN
→ не может повысить себя до ADMIN
→ не может повысить другого пользователя до ADMIN
→ не может создать административную учётную запись
```

Backend V1 также поддерживает снятие глобальных административных полномочий. Такая операция доступна только ADMIN и не удаляет саму учётную запись: после снятия полномочий она становится обычной non-admin учётной записью и далее работает по ACL/effective permissions.

При этом действует обязательный инвариант:

```text
в системе всегда существует как минимум один ADMIN
```

Поэтому:

```text
admins = {A}
A снимает admin powers с A
→ запрещено
```

```text
admins = {A, B}
A снимает admin powers с B
→ допустимо
```

Если администраторов несколько, ADMIN также может снять полномочия с самого себя; после этого его последующие операции выполняются уже как non-admin.

Только ADMIN может административно управлять login и password других существующих учётных записей:

```text
ADMIN
→ CHANGE USER LOGIN
→ RESET USER PASSWORD
```

Административный `RESET PASSWORD` не требует знания текущего password и не предоставляет возможность его прочитать. Успешный reset прекращает действие всех ранее выданных сессий и всех существовавших renewal-basis целевой учётной записи.

Обычный пользователь:

```text
→ не может изменить свой login
→ не может изменить login другого пользователя
→ не может выполнить administrative password reset
```

При этом каждый аутентифицированный пользователь, включая ADMIN в отношении собственной учётной записи, может самостоятельно изменить **собственный** password через отдельный self-service процесс с подтверждением текущего password.

### SCOPE-AUTH

Backend V1 использует для обычной password-authentication действующие `login` и `password` существующей учётной записи.

Scope включает:

- создание ADMIN обычных учётных записей с первоначальными login/password;
- authentication пользователя по действующим login/password;
- пользовательские sessions;
- session renewal;
- получение данных текущего пользователя;
- самостоятельную смену password собственной учётной записи;
- административный reset password существующей учётной записи;
- административное изменение login существующей учётной записи;
- отдельное административное предоставление и снятие global administrative powers.

Самостоятельная регистрация пользователей в Backend V1 не поддерживается.

Пользователь самостоятельно login не изменяет. Самостоятельная смена password допускается только для собственной учётной записи:

```text
USER
+ valid session
+ correct current password
+ valid new password
→ password changed
```

При успешной самостоятельной смене password:

```text
new password
→ становится действующим

old password
→ перестаёт действовать

session, где выполнена смена
→ остаётся действительной

другие существующие sessions этой account
→ становятся недействительными

все renewal basis,
существовавшие до смены password
→ становятся недействительными
```

Если session отсутствует/истекла/недействительна, current password неверен либо новый password недопустим:

```text
→ password не изменяется
→ sessions не изменяются
→ renewal basis не изменяются
```

Административный reset имеет другую семантику:

```text
ADMIN
+ valid administrative session
+ existing target account
+ valid new password
→ new password becomes current
→ old password stops working
→ ALL existing target sessions invalidated
→ ALL existing target renewal basis invalidated
```

Reset не требует текущего password и применим, в частности, когда пользователь забыл его и поэтому не может выполнить обычный self-service `CHANGE PASSWORD`.

После административного reset пользователь должен снова пройти authentication с новым password. Если ADMIN выполняет reset собственного password через административный процесс, его текущая administrative session также относится к sessions целевой учётной записи и после успешного reset становится недействительной.

Изменение login выполняется только ADMIN:

```text
ADMIN
+ valid administrative session
+ existing account
+ valid free login
→ login changed
```

Login не является идентичностью учётной записи. Изменение login не создаёт нового пользователя и само по себе не прекращает существующие sessions или renewal basis. Старый login перестаёт использоваться для password-authentication этой учётной записи, новый login используется вместо него.

Пользовательская сессия имеет ограниченный срок действия и после его истечения перестаёт быть действительной. Для продолжения работы пользователь должен успешно получить новую действующую сессию на основании ранее установленной сессии либо пройти повторную аутентификацию.

Система поддерживает получение новой пользовательской сессии без повторного ввода login/password, если у пользователя имеется действительное основание, связанное с ранее установленной пользовательской сессией и не аннулированное сменой/reset password.

Если получить новую сессию на этом основании невозможно, пользователь должен пройти authentication повторно с текущими credentials.

Защищённые операции выполняются только в рамках действующей пользовательской сессии.

Технический способ хранения и проверки password, формат стабильной identity учётной записи, а также конкретные правила допустимости login/password на уровне `RequirementsAnalysis` не определяются.

### SCOPE-INITIAL-ADMIN

При первоначальном развёртывании или инициализации системы должна быть создана первоначальная административная учётная запись с первоначальными credentials, включающими login и password, достаточными для последующей authentication, без участия уже существующего администратора и вне обычного процесса создания пользовательских учётных записей.

Конкретный технический механизм создания initial ADMIN, а также способ задания или предоставления его initial login/password на уровне `RequirementsAnalysis` не определяется.

Это единственное исключение из обычной цепочки:

```text
existing ADMIN
→ grants administrative powers
→ additional ADMIN
```

Initial ADMIN появляется до того, как такой existing ADMIN вообще существует.

### SCOPE-FILE-TREE

Управление иерархическим файловым деревом: создание папок, просмотр содержимого доступной папки с получением сведений о непосредственных дочерних элементах, включая метаданные перечисленных файлов, переименование, перемещение и удаление файлов и папок, а также отдельное прямое получение метаданных конкретного файла.

### SCOPE-FILE-CONTENT

Загрузка новых файлов, скачивание исходного содержимого файлов при наличии разрешения на такую операцию и изменение содержимого существующих файлов при наличии соответствующего разрешения, включая загрузку больших файлов с возможностью продолжения незавершённой передачи.

### SCOPE-CONTROLLED-VIEW

Просмотр содержимого файла является самостоятельной операцией относительно получения исходного файла. При `VIEW` система предоставляет отдельное представление содержимого, пригодное для просмотра, и **не выдаёт через эту операцию исходный файл или его исходные байты**.

Для non-admin представление доступно при действующем разрешении `VIEW` независимо от наличия `DOWNLOAD`. Если у пользователя одновременно есть `VIEW` и `DOWNLOAD`, операция `VIEW` всё равно выдаёт controlled representation; исходный файл относится к отдельной операции скачивания. Та же семантика `VIEW` применяется к администратору: административные полномочия позволяют ему отдельно выполнить `DOWNLOAD`, но не превращают `VIEW` в скачивание оригинала.

```text
VIEW = разрешено
DOWNLOAD = запрещено
→ controlled representation доступно
→ original bytes через VIEW не выдаются

VIEW = разрешено
DOWNLOAD = разрешено
→ VIEW всё равно выдаёт controlled representation
→ original получается только отдельной DOWNLOAD-операцией
```

Гарантия controlled view относится к **серверной выдаче данных**, а не к DRM. Backend V1 не гарантирует невозможность скриншота, фотографирования экрана, копирования уже отображённого текста или иных действий пользователя после получения представления.

Конкретный формат представления и технический способ его формирования на уровне `RequirementsAnalysis` не определяются.

### SCOPE-FILE-AUDIT

File audit разделяет два разных понятия.

**Audit history** содержит зафиксированные успешные действия **всех пользователей**, включая пользователей с глобальными административными полномочиями. Если обычный пользователь или ADMIN успешно выполняет `UPLOAD`, `VIEW`, `DOWNLOAD` или `UPDATE`, соответствующее действие относится к истории активности выбранного файла. Для каждого зафиксированного действия должны быть известны как минимум файл, пользователь, вид действия и время.

Успешный `VIEW` считается просмотром. Успешный `DOWNLOAD` original также считается просмотром с точки зрения факта ознакомления. `UPDATE` сам по себе просмотром не является.

**Current unviewed users** — отдельное множество. В него могут входить только пользователи **без глобальных административных полномочий**, которым файл доступен в текущий момент через действующие ACL и effective permissions и для которых ещё нет успешного `VIEW` или `DOWNLOAD` этого файла.

Глобальный административный доступ ко всем файлам не является основанием для попадания ADMIN в current unviewed users:

```text
NON-ADMIN
+ файл сейчас доступен через ACL/effective permissions
+ successful VIEW отсутствует
+ successful DOWNLOAD отсутствует
→ входит в current unviewed users
```

```text
ADMIN
+ имеет глобальный доступ независимо от ACL
+ successful VIEW отсутствует
+ successful DOWNLOAD отсутствует
→ не входит в current unviewed users
```

При этом действия ADMIN не исключаются из audit history:

```text
ADMIN выполняет UPLOAD / VIEW / DOWNLOAD / UPDATE
→ успешное действие фиксируется в audit history
```

Подробная информация об активности пользователей в отношении файла доступна только администратору системы. Пользователи без глобальных административных полномочий не могут получать ни audit history, ни сведения о current unviewed users.

Исторический факт действия и текущие права доступа — независимые понятия. Например:

```text
B successfully UPLOAD file.pdf
→ audit фиксирует B как пользователя, выполнившего UPLOAD
→ из этого не следуют дополнительные permissions на file.pdf
```

### SCOPE-ACL

Только администратор системы назначает пользователям наборы разрешений в отношении выбранных папок, изменяет назначенные наборы и отзывает доступ. Назначенный набор разрешений наследуется на вложенные элементы и используется для проверки разрешённости операций пользователя над доступными объектами.

### SCOPE-INDEPENDENT-PERMISSIONS

Для любого пользователя, не обладающего глобальными административными полномочиями, разрешённость файловых операций над ресурсом определяется исключительно его действующими effective permissions. Создание папки или загрузка файла сами по себе не предоставляют выполнившему операцию пользователю дополнительных permissions и не создают отдельной роли с особыми правами.

Независимо определяются разрешения на:

- просмотр содержимого папки с получением сведений о перечисленных элементах, включая метаданные перечисленных файлов;
- прямое получение метаданных конкретного файла;
- просмотр содержимого файла;
- получение исходного файла;
- создание папок;
- загрузку новых файлов;
- изменение содержимого файла;
- переименование;
- перемещение;
- удаление.

Допустима любая комбинация этих разрешений, включая пустой набор.

`LIST_FOLDER` включает не только перечисление непосредственных дочерних элементов, но и метаданные файлов, включённых в результат этого перечисления. Поэтому для метаданных, получаемых **как часть результата `LIST_FOLDER`**, отдельное разрешение `GET_FILE_METADATA` не требуется.

Это не означает, что `LIST_FOLDER` технически вызывает отдельный `BP-FILE-TREE-GET-FILE-METADATA`. Прямой запрос метаданных конкретного файла остаётся самостоятельной операцией и требует собственного разрешения `GET_FILE_METADATA`.

Односторонняя семантика:

```text
LIST_FOLDER
→ перечислить доступные непосредственные дочерние элементы
→ получить метаданные перечисленных файлов

GET_FILE_METADATA
→ напрямую получить метаданные конкретного файла
→ не предоставляет LIST_FOLDER
```

Иными словами:

```text
LIST_FOLDER ⇒ метаданные файлов, перечисленных LIST_FOLDER
GET_FILE_METADATA ⇏ LIST_FOLDER
```

Допустима назначенная комбинация:

```text
LIST_FOLDER = разрешено
GET_FILE_METADATA = запрещено
```

В этом случае пользователь получает метаданные файлов в составе listing, но отдельный прямой запрос `GET_FILE_METADATA` без соответствующего permission не выполняется.

Обратная комбинация также допустима:

```text
LIST_FOLDER = запрещено
GET_FILE_METADATA = разрешено
```

В этом случае пользователь может напрямую получить метаданные доступного ему конкретного файла, но не может перечислять содержимое родительской папки.

Для `MOVE` используется одно и то же разрешение в двух контекстах. Non-admin может переместить существующий файл или папку в другую папку только когда `MOVE` действует:

1. для самого перемещаемого объекта;
2. для размещения перемещаемого объекта в целевой папке.

Это **не означает** использование `UPLOAD` для файла или `CREATE_FOLDER` для папки: эти разрешения относятся к созданию новых объектов, а `MOVE` изменяет положение уже существующего объекта.

```text
MOVE на объекте = разрешено
MOVE в целевой папке = разрешено
UPLOAD = запрещено
CREATE_FOLDER = запрещено
→ существующий объект может быть перемещён,
  если остальные проверки операции успешны
```

Для `DELETE` папки non-admin должен иметь разрешение `DELETE` на самой удаляемой папке и на каждом её потомке. Система определяет поддерево внутренне; наличие `LIST_FOLDER` для этой проверки не требуется.

```text
DELETE на root = разрешено
DELETE на каждом descendant = разрешено
→ поддерево может быть удалено,
  если остальные проверки успешны

DELETE отсутствует хотя бы на одном descendant
→ не удаляется ничего
→ скрытый descendant не раскрывается
```

Право просмотра содержимого файла не предоставляет право получения исходного файла. Право создания папок не предоставляет право загрузки новых файлов, и право загрузки новых файлов не предоставляет право создания папок. Право загрузки нового файла не предоставляет автоматически право изменять, переименовывать, перемещать или удалять этот файл. Право переименования не предоставляет право перемещения, и право перемещения не предоставляет право переименования. Создание или загрузка объекта пользователем не предоставляет ему автоматически дополнительных разрешений на этот объект. Администратор системы является единственным пользователем, чьи глобальные административные полномочия позволяют выполнять файловые операции независимо от ACL/effective permissions.

### SCOPE-HIDDEN-ANCESTORS

Пользователь, которому предоставлен доступ к вложенной папке, видит эту папку и доступное содержимое внутри неё, но не получает доступ и не видит родительскую структуру, если отдельного права на неё у него нет.

Для проверок уникальности имени действует узкое исключение. `CREATE_FOLDER`, `UPLOAD`, `RENAME` и `MOVE` обязаны учитывать все непосредственные дочерние элементы соответствующей родительской или целевой папки, включая скрытые и недоступные пользователю. Если выбранное имя занято таким объектом, операция не выполняется.

Для non-admin в этом случае допустимо раскрыть только:

```text
выбранное имя недоступно / занято
```

Сам этот факт **не считается запрещённым раскрытием скрытого объекта**. При этом запрещено раскрывать идентификатор, тип, метаданные, положение или любые иные сведения о конфликтующем скрытом объекте. Это исключение не предоставляет `LIST_FOLDER`, `GET_FILE_METADATA` или иные права на скрытый объект.

Ограничение скрытия структуры не распространяется на администратора системы с глобальными административными полномочиями.

### SCOPE-CHANGE-LOG

Формирование единого упорядоченного журнала изменений файлового дерева и прав доступа, пригодного для последующей синхронизации клиентов.

Изменения global administrative powers также являются изменениями прав доступа и должны присутствовать в этом журнале:

```text
GRANT_ADMIN
→ изменение административного доступа
→ change log entry обязательна

REVOKE_ADMIN
→ изменение административного доступа
→ change log entry обязательна
```

Для любого изменения, которое по требованиям должно фиксироваться в этом журнале, успешное применение изменения и появление соответствующей записи в журнале образуют **единый успешный результат операции**. Не допускается состояние, в котором такое изменение считается успешно применённым, но соответствующая запись отсутствует в журнале изменений.

### SCOPE-DELETION-TRACKING

Удаление файла или папки должно фиксироваться как изменение, доступное через протокол синхронизации, чтобы клиент мог корректно отразить удаление в своём локальном состоянии.

Если удаляется папка вместе со всем поддеревом, change log должен содержать достаточное отражение удаления **всех затронутых объектов**, чтобы sync-клиенты могли убрать их из локального состояния. Требования пока не определяют, представляется это одной записью поддерева или несколькими записями объектов.

### SCOPE-SYNC-PROTOCOL

Сервер предоставляет через API инкрементальный результат синхронизации, формируемый на основе изменений единого упорядоченного журнала после позиции, указанной sync-клиентом.

Sync-клиент самостоятельно хранит локально позицию последнего успешно обработанного результата и передаёт её серверу при последующих запросах. Сервер **не хранит per-client/per-device cursor** и не требует регистрации устройства для ведения такой позиции.

Для non-admin результат синхронизации не должен раскрывать изменения, объекты или родительскую структуру, которые пользователю не разрешено раскрывать. При этом фильтрация чужих или скрытых изменений не должна мешать клиенту продвигаться по глобальному журналу: серверный результат сообщает семантическую позицию журнала, до которой он сформирован, и после успешной обработки клиент может сохранить эту позицию локально.

Sync-result должен быть достаточен для приведения локального состояния к актуальному состоянию доступных пользователю ресурсов, включая изменения доступа:

```text
ресурс был доступен
→ ресурс удалён
→ sync позволяет убрать его из локального состояния
```

```text
ресурс / поддерево было доступно
→ ACL изменён
→ доступ фактически утрачен
→ sync позволяет убрать соответствующее локальное состояние
```

```text
ресурс / поддерево уже существовало
→ ACL изменён
→ ресурс стал доступен пользователю
→ sync позволяет получить достаточное актуальное состояние
  вновь доступных ресурсов,
  даже если сами они не менялись после cursor
```

Изменение административного статуса имеет ту же observable-семантику изменения области доступа:

```text
NON-ADMIN
→ GRANT_ADMIN
→ пользователь получает global access
→ sync позволяет получить актуальное состояние
  ресурсов, ставших доступными из-за admin powers
```

```text
ADMIN
→ REVOKE_ADMIN
→ global bypass исчезает
→ ресурсы, не доступные через обычные ACL,
  должны быть убраны из локального состояния
```

Таким образом, протокол не обязан выдавать non-admin пользователю raw-записи глобального change log. Он обязан выдать основанный на журнале результат, достаточный для безопасной конвергенции локального состояния без раскрытия недоступных ресурсов.

Клиент изменяет локально сохранённую позицию только после успешной обработки полученного результата. Если обработка не завершена успешно, прежняя локальная позиция сохраняется.

На уровне `RequirementsAnalysis` не определяются:

- технический формат cursor;
- формат change events;
- способ представления появления или утраты доступа;
- batching;
- pagination;
- response size limits;
- политика retention журнала.

### SCOPE-VERSIONING

Система хранит текущую версию каждого изменяемого файла или узла. Изменение содержимого, переименование и перемещение существующего объекта выполняются относительно известной вызывающей стороне версии объекта и при успешном выполнении изменяют его текущую версию. Удаление существующего объекта также выполняется относительно известной вызывающей стороне версии и должно отклоняться, если эта версия устарела.

При удалении папки вместе с поддеревом caller-known version проверяется для **корневой удаляемой папки**. Отдельные известные клиенту версии каждого descendant для запуска удаления поддерева не требуются.

Создание новой папки или загрузка нового файла не требуют версии создаваемого объекта, поскольку до операции он не существует.

### SCOPE-CONFLICT

Конфликтующее изменение существующего объекта, основанное на устаревшей версии, отклоняется без автоматического разрешения конфликта сервером.

# Акторы

## ACTOR-ADMIN

**Родительский актор:** ACTOR-USER

Пользователь с глобальными административными полномочиями, который может работать со всеми файлами и папками системы, управлять доступом к ним, создавать обычные учётные записи пользователей с первоначальными credentials, предоставлять существующим пользователям global administrative powers, снимать такие полномочия при сохранении хотя бы одного ADMIN, изменять login существующих учётных записей, выполнять reset password существующих учётных записей без знания текущего password и выполнять остальные административные операции независимо от назначенных прав доступа.

Как наследник `ACTOR-USER`, ADMIN также может использовать обычный self-service `CHANGE PASSWORD` для собственной учётной записи.

## ACTOR-ANONYMOUS-USER

Неаутентифицированный пользователь, который может аутентифицироваться в системе или получить новую пользовательскую сессию без повторного ввода аутентификационных данных при наличии действительного основания, связанного с ранее установленной сессией.

## ACTOR-USER

Аутентифицированный пользователь облачного хранилища, который работает с доступными ему файлами и папками и может изменить password только собственной учётной записи при подтверждении текущего password. Самостоятельное изменение login пользователю не предоставляется.

## ACTOR-SHARED-USER

**Родительский актор:** ACTOR-USER

Пользователь в контексте файлов и папок, доступ к которым ему предоставлен через ACL; его действия определяются действующими effective permissions.

## ACTOR-SYNC-CLIENT

Будущий клиент облачного хранилища, действующий от имени аутентифицированного пользователя и представляющий конкретное клиентское устройство, который использует серверный протокол изменений для синхронизации локального состояния.

# Бизнес-правила

## BR-ADMIN-AT-LEAST-ONE-ADMIN — в системе всегда остаётся хотя бы один администратор

После первоначальной инициализации в системе всегда должна существовать как минимум одна учётная запись с глобальными административными полномочиями.

Initial ADMIN создаётся согласно `SCOPE-INITIAL-ADMIN` и является единственным случаем, когда появление администратора не требует уже существующего ADMIN.

После bootstrap:

```text
existing NON-ADMIN account
+
authenticated existing ADMIN performs GRANT_ADMIN
→ account becomes ADMIN
```

Обычный пользователь не может предоставить administrative powers себе или другому пользователю.

Снятие полномочий допустимо только если инвариант сохраняется:

```text
admins = {A}
REVOKE_ADMIN(A)
→ запрещено
```

```text
admins = {A, B}
A performs REVOKE_ADMIN(B)
→ допустимо
→ admins = {A}
```

```text
admins = {A, B}
A performs REVOKE_ADMIN(A)
→ допустимо
→ admins = {B}
→ A становится NON-ADMIN
```

Если позднее Backend V1 или следующая версия получит удаление пользовательских учётных записей, тот же инвариант распространяется на удаление ADMIN: операция удаления последней административной учётной записи должна быть запрещена.

**Связи:** ACTOR-ADMIN, SCOPE-ADMINISTRATION, SCOPE-AUTH, SCOPE-INITIAL-ADMIN, UC-ADMIN-GRANT-ADMIN, UC-ADMIN-REVOKE-ADMIN, BP-ADMIN-GRANT-ADMIN, BP-ADMIN-REVOKE-ADMIN

## BR-AUTH-PASSWORD-NON-DISCLOSURE — password не является выдаваемыми данными учётной записи

Текущий password учётной записи не должен возвращаться системой:

```text
current password
→ не выдаётся пользователю этой account
→ не выдаётся ADMIN
→ не выдаётся другому USER
```

Пользователь передаёт текущий password как входное подтверждение при `BP-AUTH-CHANGE-PASSWORD`, однако успешная проверка не означает возврат этого password пользователю.

Administrative reset:

```text
ADMIN
→ задаёт new password
→ current password не получает
→ current password знать не обязан
```

При `BP-ADMIN-CREATE-USER` ADMIN сам задаёт initial password. Это не создаёт возможности позднее запросить через систему действующий password этой учётной записи.

Технический способ хранения, представления и проверки password на уровне `RequirementsAnalysis` не определяется.

**Связи:** ACTOR-USER, ACTOR-ADMIN, SCOPE-AUTH, SCOPE-ADMINISTRATION, UC-ADMIN-CREATE-USER, UC-AUTH-AUTHENTICATE, UC-AUTH-CHANGE-PASSWORD, UC-ADMIN-RESET-USER-PASSWORD, BP-ADMIN-CREATE-USER, BP-AUTH-CHANGE-PASSWORD, BP-ADMIN-RESET-USER-PASSWORD

## BR-ACCOUNT-STABLE-IDENTITY — login не является identity пользователя

Каждая пользовательская учётная запись имеет стабильную identity, отличную от login.

```text
user identity ≠ login
```

Login — изменяемое аутентификационное имя существующей учётной записи.

При административной смене login:

```text
ADMIN changes login
→ тот же user identity
→ те же ACL assignments
→ та же audit history
→ тот же administrative status
→ тот же password
→ меняется login для последующей password-authentication
```

Изменение login не создаёт новую учётную запись.

Существующие sessions и renewal basis связаны со стабильной identity учётной записи, а не с текстом login. Поэтому успешная смена login сама по себе их не прекращает:

```text
login changed
→ existing sessions remain
→ existing valid renewal basis remain
```

После successful login change:

```text
old login
→ больше не используется для password-authentication этой account

new login
→ используется вместо него
```

Изменение или reset password также не меняют стабильную identity учётной записи.

Конкретный технический формат stable identity (`UUID`, integer и т. п.) на уровне `RequirementsAnalysis` не определяется.

**Связи:** ACTOR-USER, ACTOR-ADMIN, SCOPE-AUTH, SCOPE-ADMINISTRATION, UC-ADMIN-CREATE-USER, UC-AUTH-AUTHENTICATE, UC-AUTH-GET-CURRENT-USER, UC-AUTH-CHANGE-PASSWORD, UC-ADMIN-RESET-USER-PASSWORD, UC-ADMIN-CHANGE-USER-LOGIN, BP-ADMIN-CREATE-USER, BP-AUTH-CHANGE-PASSWORD, BP-ADMIN-RESET-USER-PASSWORD, BP-ADMIN-CHANGE-USER-LOGIN

## BR-FILE-TREE-UNIQUE-CHILD-NAME — уникальность имени непосредственного дочернего элемента

В одной родительской папке не допускается существование двух **разных** непосредственных дочерних элементов с одинаковым именем независимо от типа объекта.

Для файла именем считается **полное имя вместе с расширением**, если расширение присутствует. Расширение является частью имени и не отделяется при проверке уникальности.

Поэтому:

```text
папка 1     + файл 1.png  → допустимо
папка 1     + файл 1      → конфликт
папка 1.png + файл 1.png  → конфликт
файл 1.png  + файл 1.jpg  → допустимо
```

Сравнение имён для определения sibling-конфликта выполняется **без учёта регистра**. Имена, различающиеся только регистром символов, считаются одинаковыми:

```text
1.png      + 1.PNG      → конфликт
Report.pdf + report.PDF → конфликт
Folder     + folder     → конфликт
```

Последнее правило действует независимо от типов объектов: `Folder` и `folder` конфликтуют и как две папки, и как файл с папкой, если сравниваемые полные имена совпадают без учёта регистра.

Система при этом сохраняет исходное написание имени, заданное пользователем, для отображения. Case-insensitive comparison используется именно для определения конфликта и не означает нормализацию отображаемого имени.

При проверке `RENAME` и `MOVE` сам переименовываемый или перемещаемый объект не считается конфликтом с самим собой.

Правило одинаково применяется к:

- `UC-FILE-TREE-CREATE-FOLDER`;
- `UC-FILE-CONTENT-UPLOAD`;
- `UC-FILE-TREE-RENAME`;
- `UC-FILE-TREE-MOVE`.

Следствия:

```text
CREATE_FOLDER
→ имя проверяется case-insensitive против полных имён всех siblings

UPLOAD
→ полное имя файла, включая extension, проверяется case-insensitive против всех siblings

RENAME
→ новое полное имя проверяется case-insensitive против других siblings того же parent

MOVE
→ полное имя перемещаемого объекта проверяется case-insensitive против siblings target-папки
```

**Связь:** SCOPE-FILE-TREE

## BR-FILE-TREE-HIDDEN-NAME-CONFLICT-DISCLOSURE — раскрытие только недоступности имени при конфликте со скрытым sibling

Проверка `BR-FILE-TREE-UNIQUE-CHILD-NAME` учитывает **все** непосредственные дочерние элементы соответствующей родительской или целевой папки независимо от того, доступны или видимы они пользователю.

Для скрытых и недоступных siblings используется **та же семантика сравнения имён**: полное имя файла включает расширение, а сравнение выполняется без учёта регистра.

Если выбранное имя конфликтует со скрытым или недоступным объектом:

```text
CREATE_FOLDER / UPLOAD / RENAME / MOVE
→ операция не выполняется
→ допустимо сообщить только: имя недоступно / занято
```

Для non-admin сам факт недоступности выбранного имени **не считается запрещённым раскрытием скрытого объекта**. Однако система не должна раскрывать о конфликтующем скрытом объекте:

- идентификатор;
- тип;
- метаданные;
- положение;
- любые иные сведения.

Сам факт недоступности имени не предоставляет дополнительных permissions и не делает скрытый объект доступным для `LIST_FOLDER`, `GET_FILE_METADATA` или иных операций.

Правило применяется к:

- `UC-FILE-TREE-CREATE-FOLDER`;
- `UC-FILE-CONTENT-UPLOAD`;
- `UC-FILE-TREE-RENAME`;
- `UC-FILE-TREE-MOVE`.

**Связи:** SCOPE-FILE-TREE, SCOPE-HIDDEN-ANCESTORS, BR-FILE-TREE-UNIQUE-CHILD-NAME

## BR-VERSIONING-CURRENT-VERSION-AVAILABILITY — доступность current version для разрешённых операций

Для существующего объекта, который вызывающая сторона может использовать в разрешённой ей операции `RENAME`, `MOVE`, `DELETE` или `UPDATE`, система должна предоставлять вызывающей стороне текущую версию объекта, необходимую для caller-known version проверки, даже если у неё отсутствуют `LIST_FOLDER` и `GET_FILE_METADATA`.

`current version` здесь является **операционным состоянием**, необходимым для выполнения разрешённой операции с optimistic conflict check, а не самостоятельным разрешением на чтение metadata или content.

Таким образом, допустима комбинация:

```text
UPDATE = разрешено
LIST_FOLDER = запрещено
GET_FILE_METADATA = запрещено
VIEW = запрещено
DOWNLOAD = запрещено

→ current version файла всё равно доступна вызывающей стороне
  в объёме, необходимом для выполнения UPDATE
→ дополнительные metadata или content из этого не следуют
```

То же правило применяется к `RENAME`, `MOVE` и `DELETE`.

Предоставление current version само по себе **не предоставляет**:

- `LIST_FOLDER`;
- `GET_FILE_METADATA`;
- `VIEW`;
- `DOWNLOAD`;
- другие файловые permissions.

Оно также не должно раскрывать дополнительные метаданные, содержимое или недоступную родительскую структуру объекта.

Требования намеренно не определяют, каким техническим способом current version предоставляется клиенту: как часть результата другой разрешённой операции, через отдельное представление операционного состояния или иным способом. Это определяется ниже уровня `RequirementsAnalysis`.

Правило применяется к:

- `UC-FILE-TREE-RENAME`;
- `UC-FILE-TREE-MOVE`;
- `UC-FILE-TREE-DELETE`;
- `UC-FILE-CONTENT-UPDATE`.

**Связи:** SCOPE-VERSIONING, SCOPE-CONFLICT, SCOPE-INDEPENDENT-PERMISSIONS, SCOPE-HIDDEN-ANCESTORS

## BR-ACL-EFFECTIVE-PERMISSIONS — вычисление эффективного набора ACL-разрешений

Назначенный пользователю permission set на папке действует на саму эту папку и наследуется на всё её поддерево. Дополнительные ACL-назначения на вложенных папках **не заменяют** унаследованные разрешения, а добавляются к ним.

Для папки эффективный набор равен объединению всех ACL-наборов, назначенных пользователю:

- на самой папке;
- на всех её предках.

Для файла эффективный набор равен объединению всех ACL-наборов, назначенных пользователю:

- на содержащей файл папке;
- на всех предках этой папки.

Иными словами:

```text
effective_permissions(object, user)
=
UNION(all applicable ACL permission sets for user)
```

Если одно и то же permission присутствует в нескольких применимых назначениях, в effective set оно учитывается один раз.

Пример объединения:

```text
A → {VIEW}
└── B → {DOWNLOAD}
    └── file.pdf
```

Для `file.pdf`:

```text
effective permissions = {VIEW, DOWNLOAD}
```

Назначение на `B` не перекрывает `{VIEW}`, унаследованный от `A`.

Пустой набор не имеет subtractive-семантики:

```text
A → {VIEW, DOWNLOAD}
└── B → {}
```

Для `B` и его descendants:

```text
effective permissions = {VIEW, DOWNLOAD}
```

`{}` остаётся существующим ACL-назначением, но сам по себе ничего не добавляет и ничего не отнимает.

`REVOKE` удаляет только конкретное назначение. Например:

```text
A → {VIEW}
└── B → {DOWNLOAD}
```

После `REVOKE` назначения `{DOWNLOAD}` на `B`:

```text
B → assignment отсутствует
effective permissions на B и descendants = {VIEW}
```

Унаследованный от `A` `VIEW` сохраняется. Аналогично, если удалённое назначение предоставляло permission, которое всё ещё приходит через другое применимое назначение, это permission остаётся в effective set.

Таким образом, ACL-модель Backend V1 является **additive union model**: более глубокое назначение может только добавить разрешения к другим применимым назначениям; пустой set не отнимает разрешения; `REVOKE` удаляет только конкретное основание доступа.

**Связи:** SCOPE-ACL, SCOPE-INDEPENDENT-PERMISSIONS, BP-ADMIN-MANAGE-ACCESS, UC-ADMIN-GRANT-ACCESS, UC-ADMIN-CHANGE-ACCESS, UC-ADMIN-REVOKE-ACCESS

# Бизнес-процессы

## BP-ADMIN-CREATE-USER — создание обычной учётной записи администратором

Аутентифицированный ADMIN создаёт новую обычную учётную запись пользователя без global administrative powers и задаёт initial credentials — login и password.

**Последовательность:**

1. **Передача данных.** ADMIN передаёт данные новой обычной учётной записи, включая initial login и initial password, достаточные для последующей authentication.
2. **Проверка административной сессии.** Система проверяет действующую пользовательскую session и наличие global administrative powers у текущей учётной записи. Без обоих условий учётная запись не создаётся.
3. **Проверка данных.** Система проверяет достаточность и допустимость данных, включая допустимость initial login/password. При ошибке account не создаётся.
4. **Проверка существующей учётной записи.** Initial login и другие данные, для которых требуется отсутствие конфликта, не должны конфликтовать с существующей account. Если конфликт есть, новая account не создаётся. Конкретные правила нормализации/comparison login на этом уровне не определяются.
5. **Создание учётной записи.** Система создаёт новую account со стабильной identity, указанным initial login и действующим initial password, без global administrative powers.

**Успешный результат:** существует новая non-admin account со стабильной identity и initial credentials, которыми пользователь может воспользоваться для последующей самостоятельной authentication.

```text
BP-ADMIN-CREATE-USER
→ account created
→ stable identity exists
→ initial login active
→ initial password active
→ ADMIN = no
→ user session for new account не создаётся
```

ADMIN задаёт initial password как входные данные создания, но система не предоставляет ему возможности позднее прочитать текущий password account.

Обязательная смена password при первом входе **не вводится**.

Если позднее пользователю нужны административные полномочия, используется отдельный `BP-ADMIN-GRANT-ADMIN`.

**Связи:** ACTOR-ADMIN, UC-ADMIN-CREATE-USER, SCOPE-AUTH, SCOPE-ADMINISTRATION, BR-AUTH-PASSWORD-NON-DISCLOSURE, BR-ACCOUNT-STABLE-IDENTITY

## BP-ADMIN-GRANT-ADMIN — предоставление глобальных административных полномочий

Аутентифицированный ADMIN предоставляет global administrative powers уже существующей non-admin учётной записи. После первоначального bootstrap это единственный обычный путь превращения существующего пользователя в дополнительного ADMIN.

**Последовательность:**

1. **Выбор учётной записи.** ADMIN указывает существующую non-admin учётную запись.
2. **Проверка административной сессии.** Система проверяет, что сессия действительна и текущая учётная запись уже обладает global administrative powers. Обычный пользователь выполнить операцию не может.
3. **Проверка цели.** Целевая учётная запись должна существовать и в текущий момент быть non-admin. Если она отсутствует либо уже является ADMIN, состояние не изменяется.
4. **Предоставление полномочий и change log.** Система предоставляет global administrative powers и фиксирует это изменение прав доступа в едином change log как единый успешный результат. Существующие ACL-назначения пользователя не удаляются и не меняются. Пока admin powers действуют, они предоставляют глобальный bypass ACL и hidden-ancestor ограничений. Последующие защищённые операции должны оцениваться с учётом актуального административного статуса учётной записи.

**Успешный результат:** существующая учётная запись становится `ACTOR-ADMIN`; новая учётная запись и новая сессия не создаются.

```text
existing NON-ADMIN account
+
existing authenticated ADMIN
+
GRANT_ADMIN successful
→ account becomes ADMIN
→ admin access change recorded in change log
```

Конкретный технический способ, которым изменение административного статуса отражается в уже существующей пользовательской сессии, на уровне `RequirementsAnalysis` не определяется. Наблюдаемое требование одно: после успешной операции последующие проверки должны использовать текущий административный статус, а не устаревшее состояние.

**Связи:** ACTOR-ADMIN, UC-ADMIN-GRANT-ADMIN, SCOPE-ADMINISTRATION, SCOPE-AUTH, SCOPE-INITIAL-ADMIN, SCOPE-CHANGE-LOG, BR-ADMIN-AT-LEAST-ONE-ADMIN

## BP-ADMIN-REVOKE-ADMIN — снятие глобальных административных полномочий

Аутентифицированный ADMIN снимает global administrative powers с существующей административной учётной записи. Учётная запись при этом не удаляется, а становится обычной non-admin учётной записью.

**Последовательность:**

1. **Выбор учётной записи.** ADMIN указывает существующую административную учётную запись. Он может указать в том числе самого себя.
2. **Проверка административной сессии.** Система проверяет действительность сессии и текущие global administrative powers вызывающего пользователя. Без обоих условий операция не выполняется.
3. **Проверка цели.** Целевая учётная запись должна существовать и в текущий момент быть ADMIN.
4. **Проверка инварианта.** Система проверяет `BR-ADMIN-AT-LEAST-ONE-ADMIN`. Если выбранная учётная запись является последним текущим ADMIN, операция запрещается.
5. **Снятие полномочий и change log.** Система снимает global administrative powers и фиксирует соответствующее изменение прав доступа в едином change log. Сама учётная запись и её существующие ACL assignments сохраняются. После успешной операции файловые действия этой учётной записи определяются как для любого non-admin пользователя через применимые ACL и `BR-ACL-EFFECTIVE-PERMISSIONS`.

**Успешный результат:** выбранная учётная запись продолжает существовать, но больше не имеет административного bypass.

```text
admins = {A, B}
A revokes B
→ B becomes NON-ADMIN
→ B existing ACL assignments сохраняются
→ subsequent B file access определяется ACL/effective permissions
→ admins = {A}
```

Последнего администратора лишить полномочий нельзя:

```text
admins = {A}
REVOKE_ADMIN(A)
→ rejected
→ A remains ADMIN
```

Конкретный механизм обновления уже существующей сессии не определяется; последующие проверки обязаны использовать фактический текущий административный статус.

**Связи:** ACTOR-ADMIN, UC-ADMIN-REVOKE-ADMIN, SCOPE-ADMINISTRATION, SCOPE-AUTH, SCOPE-INITIAL-ADMIN, SCOPE-INDEPENDENT-PERMISSIONS, SCOPE-CHANGE-LOG, BR-ADMIN-AT-LEAST-ONE-ADMIN, BR-ACL-EFFECTIVE-PERMISSIONS

## BP-ADMIN-RESET-USER-PASSWORD — административный reset password

Аутентифицированный ADMIN устанавливает новый допустимый password существующей account **без знания текущего password**. Процесс предназначен в том числе для восстановления доступа пользователя, который забыл password и не может выполнить обычный self-service `CHANGE PASSWORD`.

**Последовательность:**

1. **Запрос reset.** ADMIN указывает существующую target account и новый password.
2. **Проверка административной сессии.** Система проверяет valid non-expired session вызывающего пользователя и его current global administrative powers. Если любое условие не выполняется, target password не меняется.
3. **Проверка target.** Target account должна существовать. Reset применим к обычной account, ADMIN-account и собственной account выполняющего администратора.
4. **Проверка нового password.** Новый password должен быть допустим. Current password target-account не требуется и не выдаётся. При недопустимом новом password ни password, ни session-state не изменяются.
5. **Применение и invalidation.** Если проверки успешны, система как один успешный результат устанавливает new password, прекращает действие old password, всех existing sessions target-account и всех существовавших renewal basis target-account.

Не допускается:

```text
successful ADMIN RESET PASSWORD
+
old password still authenticates
ИЛИ old session still valid
ИЛИ old renewal basis still valid
→ недопустимо
```

Если target account совпадает с account вызывающего ADMIN:

```text
ADMIN resets own password through admin reset
→ current administrative session входит в target sessions
→ после successful reset session становится invalid
```

**Успешный результат:** new password является действующим password той же account, old password больше не действует, все ранее существовавшие target sessions/renewal-basis недействительны. Для продолжения работы пользователь должен снова пройти `BP-AUTH-AUTHENTICATE` с current login и new password.

Reset не меняет stable identity, login, ACL assignments, audit history или administrative status target account.

**Связи:** ACTOR-ADMIN, UC-ADMIN-RESET-USER-PASSWORD, UC-AUTH-AUTHENTICATE, UC-AUTH-RENEW-SESSION, SCOPE-AUTH, SCOPE-ADMINISTRATION, BR-AUTH-PASSWORD-NON-DISCLOSURE, BR-ACCOUNT-STABLE-IDENTITY

## BP-ADMIN-CHANGE-USER-LOGIN — административное изменение login

Аутентифицированный ADMIN изменяет login существующей account на новый допустимый login, который не конфликтует с другой существующей account.

**Последовательность:**

1. **Запрос изменения.** ADMIN указывает target account и new login.
2. **Проверка административной сессии.** Система проверяет valid non-expired session и current global administrative powers вызывающего пользователя. При отрицательном результате login не изменяется.
3. **Проверка target.** Target account должна существовать. ADMIN может изменить login обычной account, другой ADMIN-account или собственной account.
4. **Проверка login.** New login должен быть допустим и не конфликтовать с login другой существующей account. Target account исключается из self-conflict. Конкретные normalization/comparison rules на этом уровне не определяются.
5. **Применение.** Система заменяет login той же account. Old login перестаёт использоваться для subsequent password-authentication, new login используется вместо него.

Если new login недопустим или занят:

```text
→ login не изменяется
```

Успешная смена login **не меняет identity**:

```text
same user identity
same password
same ACL assignments
same audit history
same administrative status
same existing sessions
same valid renewal basis
```

Обычный USER не может изменить ни свой login, ни чужой.

**Связи:** ACTOR-ADMIN, UC-ADMIN-CHANGE-USER-LOGIN, UC-AUTH-AUTHENTICATE, SCOPE-AUTH, SCOPE-ADMINISTRATION, BR-ACCOUNT-STABLE-IDENTITY

## BP-AUTH-AUTHENTICATE — аутентификация пользователя

Неаутентифицированный пользователь подтверждает принадлежность существующей account с помощью её **действующих login и password**.

**Последовательность:**

1. **Передача данных.** Пользователь передаёт login и password.
2. **Проверка данных.** Система проверяет, что login/password достаточны и допустимы для попытки authentication. При ошибке session не создаётся.
3. **Подтверждение account.** Система проверяет, что login/password соответствуют текущим действующим credentials одной existing account. Старый login после successful `CHANGE USER LOGIN` и старый password после successful `CHANGE PASSWORD`/`RESET PASSWORD` действующими credentials больше не являются.
4. **Начало session.** Если authentication подтверждена, система начинает user session для стабильной identity соответствующей account.

**Успешный результат:** пользователь authenticated по current login/password и получает session, от имени которой выполняет разрешённые операции.

Password проверяется, но не выдаётся как данные account.

**Связи:** UC-AUTH-AUTHENTICATE, UC-AUTH-CHANGE-PASSWORD, UC-ADMIN-RESET-USER-PASSWORD, UC-ADMIN-CHANGE-USER-LOGIN, SCOPE-AUTH, BR-AUTH-PASSWORD-NON-DISCLOSURE, BR-ACCOUNT-STABLE-IDENTITY

## BP-AUTH-RENEW-SESSION — получение новой сессии для возобновления работы

Неаутентифицированный пользователь получает новую действующую session без повторного ввода login/password, если имеется действительный renewal basis, связанный с ранее установленной session и не аннулированный credential-change.

**Последовательность:**

1. **Передача основания.** Пользователь передаёт данные renewal basis.
2. **Проверка основания.** Система проверяет существование и действительность basis. Basis, существовавший до successful `BP-AUTH-CHANGE-PASSWORD`, либо любой basis target account, существовавший до successful `BP-ADMIN-RESET-USER-PASSWORD`, после такой операции не считается действительным.
3. **Отказ при invalid basis.** Если basis invalid/expired/revoked due password change/reset либо больше не пригоден по другой причине, new session не создаётся.
4. **Определение account.** По valid basis система определяет stable identity account. Login change сам по себе связь basis с account не разрывает.
5. **Создание session.** Система создаёт новую действующую user session для определённой account.

**Успешный результат:** пользователь получает новую session без повторного ввода login/password.

Если valid basis нет, пользователь проходит обычную authentication с current credentials.

```text
old basis invalidated by password change/reset
→ cannot renew
```

```text
login changed only
→ otherwise-valid basis remains linked to same account identity
```

**Связи:** UC-AUTH-RENEW-SESSION, UC-AUTH-CHANGE-PASSWORD, UC-ADMIN-RESET-USER-PASSWORD, UC-ADMIN-CHANGE-USER-LOGIN, SCOPE-AUTH, BR-ACCOUNT-STABLE-IDENTITY

## BP-AUTH-GET-CURRENT-USER — получение текущего пользователя

Аутентифицированный пользователь получает данные stable account identity, которой соответствует current session.

**Последовательность:**

1. **Запрос данных.** Пользователь запрашивает данные current account.
2. **Проверка session.** Session должна существовать, не быть expired и оставаться valid.
3. **Определение account.** Система определяет stable identity account, которой соответствует current session.
4. **Выдача данных.** Система возвращает данные account, которые могут включать current login и administrative status, но **не включают current password**.

**Успешный результат:** пользователь получает данные своей current account без выдачи password.

Login change не меняет то, какая stable account соответствует уже существующей session.

**Связи:** UC-AUTH-GET-CURRENT-USER, SCOPE-AUTH, BR-AUTH-PASSWORD-NON-DISCLOSURE, BR-ACCOUNT-STABLE-IDENTITY

## BP-AUTH-CHANGE-PASSWORD — самостоятельная смена собственного password

Аутентифицированный USER, включая ADMIN для собственной account, меняет password **только собственной account** в valid session после подтверждения current password.

**Последовательность:**

1. **Запрос смены.** USER передаёт current password своей account и new password.
2. **Проверка session.** Current session должна существовать, не быть expired и оставаться valid. По session система определяет stable identity собственной account. При invalid session password/session-state не меняются.
3. **Подтверждение current password.** Переданный current password должен соответствовать current password той же account. Через этот процесс нельзя указать другую account. При неверном current password состояние не меняется.
4. **Проверка new password.** New password должен быть допустим. При недопустимом password состояние не меняется. Конкретные password-policy rules на этом уровне не определяются.
5. **Применение и invalidation.** Successful result одновременно:
   - делает new password действующим;
   - прекращает действие old password;
   - сохраняет действительной current session, где выполнена смена;
   - прекращает все остальные existing sessions account;
   - прекращает все renewal basis, существовавшие до смены password.

Ошибочные случаи:

```text
invalid/expired session
→ password unchanged
→ sessions unchanged
→ renewal basis unchanged
```

```text
wrong current password
→ password unchanged
→ sessions unchanged
→ renewal basis unchanged
```

```text
invalid new password
→ password unchanged
→ sessions unchanged
→ renewal basis unchanged
```

Успешный случай:

```text
new password active
old password invalid
current session remains valid
all other old sessions invalid
all pre-change renewal basis invalid
```

После завершения сохранившейся current session продолжение без reauthentication возможно только при наличии нового valid renewal basis, появившегося после password change; иначе пользователь проходит normal authentication с new password.

Stable identity, login, ACL assignments, audit history и administrative status account не изменяются.

**Связи:** ACTOR-USER, ACTOR-ADMIN, UC-AUTH-CHANGE-PASSWORD, UC-AUTH-AUTHENTICATE, UC-AUTH-RENEW-SESSION, SCOPE-AUTH, BR-AUTH-PASSWORD-NON-DISCLOSURE, BR-ACCOUNT-STABLE-IDENTITY

## BP-FILE-TREE-CREATE-FOLDER — создание папки

Аутентифицированный пользователь создаёт новую папку непосредственно внутри выбранной родительской папки, если пользовательская сессия действительна и операция создания папок разрешена для этого пользователя в отношении родительской папки либо пользователь является администратором системы. Успешное создание новой папки включает установку её первоначальной current version и фиксацию создания в едином change log.

**Последовательность:**

1. **Запрос создания.** Пользователь указывает родительскую папку и передаёт данные новой папки.
2. **Проверка сессии.** Система проверяет, что пользовательская сессия существует, не истекла и остаётся действительной. Если действительной неистёкшей сессии нет, процесс завершается без создания папки.
3. **Проверка родительской папки без раскрытия скрытой структуры.** Система определяет, может ли указанная родительская папка быть использована как объект этой операции в контексте полномочий пользователя. Для пользователя без глобальных административных полномочий отрицательный результат не позволяет определить, отсутствует ли указанная папка или она существует, но находится вне доступной пользователю области; в обоих случаях новая папка не создаётся и существование скрытого объекта не раскрывается. Для администратора ограничения скрытия родительской структуры не применяются; если указанная папка не существует, новая папка не создаётся.
4. **Проверка разрешения CREATE_FOLDER.** Если родительская папка может быть использована как объект операции, для пользователя без глобальных административных полномочий система проверяет, что действующий набор разрешений позволяет создание папок внутри неё. Отсутствие разрешений на другие операции, включая `LIST_FOLDER`, не препятствует созданию папки. Для администратора эта проверка разрешений не ограничивает операцию. Если создание папок не разрешено, новая папка не создаётся.
5. **Проверка имени.** Имя создаваемой папки проверяется по `BR-FILE-TREE-UNIQUE-CHILD-NAME` против всех непосредственных дочерних элементов parent, включая скрытые и недоступные. Сравнение выполняется без учёта регистра; если sibling является файлом, его extension входит в полное имя. Тип sibling значения не имеет. При конфликте новая папка не создаётся; для non-admin конфликт со скрытым sibling раскрывается только как «имя недоступно/занято» согласно `BR-FILE-TREE-HIDDEN-NAME-CONFLICT-DISCLOSURE`.
6. **Создание, version и change log.** Если все проверки успешны, создание новой папки непосредственно внутри выбранной родительской папки, установка initial current version, применение действующих правил ACL и наследования и фиксация создания папки в едином change log образуют один успешный результат. Нельзя считать создание успешным, если папка отсутствует в активном файловом дереве, не имеет current version или соответствующее создание отсутствует в change log.

**Успешный результат:** новая папка существует как непосредственный дочерний элемент выбранной родительской папки, не нарушает `BR-FILE-TREE-UNIQUE-CHILD-NAME`, имеет initial current version, подчиняется действующим правилам ACL и наследования, а её создание присутствует в едином change log для последующей синхронизации.

Создание новой папки **не требует caller-known version**, поскольку до операции она не существует. Сам факт создания папки **не предоставляет создавшему её пользователю дополнительных разрешений на неё**.

Для non-admin невозможность использовать указанный parent не должна позволять определить, существует ли скрытая или недоступная папка. Отдельное исключение действует только для проверки имени: `BR-FILE-TREE-HIDDEN-NAME-CONFLICT-DISCLOSURE` разрешает сообщить, что выбранное имя недоступно, не раскрывая конфликтующий скрытый объект. При этом разрешение `CREATE_FOLDER` остаётся независимым от `LIST_FOLDER` и других файловых разрешений.

Пока требования не определяют конкретный набор полей создаваемой папки, правила допустимости имени, формат initial current version, формат change-log записи или технический способ адресации родительской папки.

**Связи:**

* UC-FILE-TREE-CREATE-FOLDER
* SCOPE-FILE-TREE
* SCOPE-INDEPENDENT-PERMISSIONS
* SCOPE-VERSIONING
* SCOPE-CHANGE-LOG
* SCOPE-ACL
* SCOPE-HIDDEN-ANCESTORS
* SCOPE-ADMINISTRATION
* BR-FILE-TREE-UNIQUE-CHILD-NAME
* BR-FILE-TREE-HIDDEN-NAME-CONFLICT-DISCLOSURE

## BP-FILE-TREE-LIST-FOLDER — просмотр содержимого папки

Аутентифицированный пользователь получает перечень непосредственных дочерних элементов выбранной папки. Для файлов, включённых в этот перечень, операция также возвращает их метаданные. Для non-admin операция определяется `LIST_FOLDER`; отдельный `GET_FILE_METADATA` для метаданных внутри результата listing не требуется.

**Последовательность:**

1. **Запрос содержимого.** Пользователь указывает папку, содержимое которой хочет получить.
2. **Проверка сессии.** Система проверяет, что пользовательская сессия существует, не истекла и остаётся действительной. Если действительной неистёкшей сессии нет, содержимое папки не выдаётся.
3. **Проверка папки без раскрытия скрытой структуры.** Система определяет, может ли указанная папка быть использована как объект операции в контексте полномочий пользователя. Для non-admin отрицательный результат не позволяет определить, отсутствует ли папка или существует, но находится вне доступной пользователю области. Для администратора ограничение скрытия структуры не применяется.
4. **Проверка `LIST_FOLDER`.** Для non-admin система проверяет `LIST_FOLDER` на указанную папку. В рамках этого процесса разрешение включает как перечисление непосредственных дочерних элементов, так и метаданные файлов, включённых в результат. Отдельный `GET_FILE_METADATA` для этих метаданных не требуется. Для администратора permission check операцию не ограничивает.
5. **Формирование списка.** Система формирует перечень непосредственно находящихся в папке файлов и папок, существование которых разрешено раскрыть пользователю согласно действующим правилам ACL и скрытия структуры. Для каждого включённого файла результат содержит его метаданные; для каждого перечисленного элемента возвращаются сведения, необходимые для представления элемента в составе содержимого папки. Скрытые или недоступные объекты не включаются, а результат не позволяет определить, отсутствуют они физически или были скрыты правилами доступа. Конкретный состав метаданных файла пока не определяется.
6. **Выдача списка.** Система возвращает сформированный перечень непосредственных дочерних элементов вместе с метаданными перечисленных файлов. Отдельный прямой запрос метаданных конкретного файла остаётся самостоятельной операцией.

**Успешный результат:** пользователь получает доступные непосредственные дочерние файлы и папки выбранной папки и метаданные файлов, включённых в этот результат, без раскрытия скрытой структуры.

Семантика разрешений для этой операции:

```text
LIST_FOLDER = разрешено
GET_FILE_METADATA = запрещено
→ listing выполняется
→ перечисленные файлы возвращаются с metadata
→ отдельный прямой GET_FILE_METADATA не разрешается
```

То есть `LIST_FOLDER` включает получение метаданных перечисленных файлов как часть своего собственного результата, но не превращается в глобальное разрешение прямого получения metadata любого файла.

Если физически в папке есть элементы, которые пользователю нельзя раскрывать, результат listing не должен позволять отличить их от отсутствующих элементов. Исключение name-availability относится только к операциям, проверяющим уникальность имени, и не изменяет результат `LIST_FOLDER`.

Пока требования не определяют полный состав метаданных файла, сведения для представления папок, сортировку, пагинацию или технический способ адресации папки.

* UC-FILE-TREE-LIST-FOLDER
* SCOPE-FILE-TREE

## BP-FILE-TREE-RENAME — переименование файла или папки

Аутентифицированный пользователь изменяет имя существующего файла или папки без изменения положения объекта в файловой структуре. Для non-admin требуется отдельное разрешение `RENAME`; администратор обходит эту permission-проверку. Проверка версии обязательна для всех, включая администратора.

**Последовательность:**

1. **Запрос переименования.** Пользователь указывает файл или папку, новое имя и известную ему версию объекта.
2. **Проверка сессии.** Система проверяет, что пользовательская сессия существует, не истекла и остаётся действительной. Без действующей сессии переименование не выполняется.
3. **Проверка объекта без раскрытия скрытой структуры.** Система определяет, может ли указанный объект участвовать в операции в контексте полномочий пользователя. Для non-admin отрицательный результат не позволяет определить, отсутствует ли объект или существует, но скрыт/недоступен. Для администратора ограничение скрытия не применяется.
4. **Проверка `RENAME`.** Для non-admin проверяется отдельное разрешение переименования. Оно независимо от `LIST_FOLDER`, `GET_FILE_METADATA`, `MOVE` и остальных разрешений. Для администратора эта проверка операцию не ограничивает.
5. **Проверка имени.** Новое имя проверяется по `BR-FILE-TREE-UNIQUE-CHILD-NAME` против всех других siblings того же parent. Сравнение выполняется без учёта регистра; для файла полное имя включает extension. Сам переименовываемый объект исключается из проверки. При конфликте переименование не выполняется; для non-admin конфликт со скрытым sibling раскрывается только как недоступность/занятость выбранного имени согласно `BR-FILE-TREE-HIDDEN-NAME-CONFLICT-DISCLOSURE`.
6. **Проверка версии.** Система сравнивает известную пользователю версию объекта с текущей. Если версия устарела, переименование отклоняется как конфликт без автоматического разрешения. Администратор от этой проверки не освобождается.
7. **Применение переименования и фиксация изменения.** Если все проверки успешны, изменение имени объекта без изменения его положения, установка новой текущей версии и фиксация соответствующего изменения файлового дерева в едином упорядоченном журнале образуют единый успешный результат операции.

**Успешный результат:** тот же файл или папка находится в прежнем месте под новым именем, не конфликтующим с именем другого непосредственного дочернего элемента того же родителя, имеет новую текущую версию, а соответствующее изменение присутствует в едином журнале изменений для последующей синхронизации.

**Инвариант процесса:** не допускается успешно завершённое переименование, отсутствующее в журнале изменений. Изменение имени, изменение текущей версии и фиксация соответствующего изменения в change log рассматриваются как единый успешный результат операции.

Переименование не меняет положение объекта. Действующие правила ACL продолжают применяться к нему; само переименование **не предоставляет пользователю дополнительных разрешений**.

```text
RENAME разрешён
LIST_FOLDER запрещён
GET_FILE_METADATA запрещён
MOVE запрещён
→ переименование всё равно может быть выполнено,
  если объект может быть указан для операции и остальные проверки успешны
```

Проверка уникальности при этом всё равно учитывает скрытых siblings. Единственная допустимая утечка — факт того, что выбранное новое имя недоступно; конфликтующий скрытый объект не раскрывается.

Правило `SCOPE-CHANGE-LOG` распространяет тот же инвариант на другие изменения, для которых требования впоследствии установят обязательную фиксацию в журнале.

Пока требования не определяют правила допустимости нового имени, формат версии, формат записи change log или технический способ адресации объекта.

## BP-FILE-TREE-MOVE — перемещение файла или папки

Аутентифицированный пользователь изменяет положение существующего файла или папки в файловом дереве. Для non-admin существующее разрешение `MOVE` проверяется дважды: на самом перемещаемом объекте и в контексте целевой папки для размещения объекта. Администратор обходит эти permission-проверки. Проверка версии обязательна для всех, включая администратора. Целевая папка должна отличаться от текущей родительской папки объекта: указание текущего родителя не является перемещением.

**Последовательность:**

1. **Запрос перемещения.** Пользователь указывает перемещаемый файл или папку, целевую папку и известную ему версию перемещаемого объекта.
2. **Проверка сессии.** Система проверяет, что пользовательская сессия существует, не истекла и остаётся действительной. Без действующей сессии перемещение не выполняется.
3. **Проверка объектов без раскрытия скрытой структуры.** Система определяет, могут ли перемещаемый объект и целевая папка участвовать в операции в контексте полномочий пользователя. Для non-admin отрицательный результат в отношении любого из них не позволяет определить, отсутствует ли соответствующий объект или существует, но скрыт/недоступен. Для администратора ограничение скрытия не применяется.
4. **Проверка `MOVE`.** Для non-admin `MOVE` должен действовать и для самого перемещаемого объекта, и для размещения этого объекта в целевой папке. Проверка целевой папки использует то же permission `MOVE`, а не `UPLOAD` или `CREATE_FOLDER`. Отсутствие `LIST_FOLDER`, `GET_FILE_METADATA` и других независимых разрешений само по себе не запрещает перемещение. Для администратора permission-проверки операцию не ограничивают.
5. **Проверка фактического изменения родителя.** Целевая папка должна отличаться от текущей родительской папки перемещаемого объекта. Если выбран текущий родитель, положение объекта не изменяется, его текущая версия не изменяется, запись в change log не создаётся, и операция не считается успешно выполненным `MOVE`.
6. **Проверка иерархии.** Перемещение должно сохранять корректное дерево. Папка не может быть перемещена в саму себя или в любую свою вложенную папку.
7. **Проверка имени.** Имя перемещаемого объекта проверяется по `BR-FILE-TREE-UNIQUE-CHILD-NAME` против siblings целевой папки. Сравнение выполняется без учёта регистра; для файла полное имя включает extension. Сам перемещаемый объект исключается из проверки. При конфликте перемещение не выполняется; для non-admin конфликт со скрытым sibling раскрывается только как недоступность/занятость имени согласно `BR-FILE-TREE-HIDDEN-NAME-CONFLICT-DISCLOSURE`.
8. **Проверка версии.** Система сравнивает известную пользователю версию перемещаемого объекта с текущей. Если версия устарела, перемещение отклоняется как conflict без автоматического разрешения. Администратор от этой проверки не освобождается.
9. **Применение перемещения и фиксация изменения.** Если все проверки успешны, изменение положения объекта, установка новой текущей версии и фиксация соответствующего изменения файлового дерева в едином упорядоченном журнале образуют единый успешный результат операции.

**Успешный результат:** тот же файл или папка является непосредственным дочерним элементом выбранной целевой папки, отличной от его прежней родительской папки, не конфликтует по имени с другим непосредственным дочерним элементом этой папки, имеет новую текущую версию, а соответствующее изменение присутствует в едином change log.

**No-op:** попытка переместить объект в его текущую родительскую папку не изменяет положение объекта, текущую версию, ACL или change log и не считается успешно завершённым перемещением.

**Инвариант процесса:** не допускается успешно завершённое перемещение, отсутствующее в журнале изменений. Изменение положения, изменение текущей версии и запись в change log образуют единый успешный результат.

После перемещения действующие разрешения на объект и его вложенные элементы определяются применимыми правилами ACL и наследования уже с учётом нового положения в файловом дереве. Само перемещение дополнительных разрешений пользователю не предоставляет.

```text
MOVE на объекте = разрешено
MOVE в целевой папке = разрешено
UPLOAD = запрещено
CREATE_FOLDER = запрещено
→ перемещение существующего объекта разрешено,
  если остальные проверки успешны
```

```text
MOVE на объекте = разрешено
MOVE в целевой папке = запрещено
→ перемещение запрещено
```

```text
целевая папка = текущий родитель
→ положение не меняется
→ версия не меняется
→ change log не меняется
→ успешного MOVE нет
```

Проверка уникальности имени в target учитывает и скрытых siblings; при таком конфликте допустимо раскрыть только недоступность имени.

Пока требования не определяют формат версии, формат записи change log или технический способ адресации объектов.

## BP-FILE-TREE-DELETE — удаление файла или поддерева папки

Аутентифицированный пользователь удаляет существующий файл или папку. Удаление папки означает удаление **всей папки вместе со всеми потомками как одной логической операции**. Для non-admin `DELETE` должен действовать на каждом затрагиваемом объекте. Администратор обходит permission-проверки. Caller-known version проверяется для root удаляемого объекта.

**Последовательность:**

1. **Запрос удаления.** Пользователь указывает удаляемый root — файл или папку — и известную ему версию root.
2. **Проверка сессии.** Система проверяет, что пользовательская сессия существует, не истекла и остаётся действительной. Без действующей сессии удаление не выполняется.
3. **Разрешение root без раскрытия скрытой структуры.** Система определяет, может ли root участвовать в операции. Для non-admin отрицательный результат не позволяет определить, отсутствует ли root или существует, но скрыт/недоступен. Для администратора ограничение скрытия не применяется.
4. **Определение затрагиваемого поддерева.** Для файла затрагивается только сам файл. Для папки система внутренне определяет root и всех descendants. Это не требует `LIST_FOLDER` и не раскрывает пользователю скрытые вложенные объекты.
5. **Проверка `DELETE`.** Для non-admin `DELETE` должен действовать на root и каждый descendant. Если разрешения нет хотя бы на одном затрагиваемом объекте, **не удаляется ничего**. Отказ не должен идентифицировать скрытый descendant или раскрывать структуру поддерева. Для администратора permission-проверки операцию не ограничивают.
6. **Проверка версии root.** Известная пользователю версия root сравнивается с текущей версией root. При stale version всё удаление отклоняется как conflict без автоматического разрешения. Отдельные caller-known versions descendants не требуются. Проверка root-version обязательна и для администратора.
7. **Удаление и фиксация изменений.** Если все проверки успешны, удаление root и всех descendants вместе с достаточным отражением удаления каждого затронутого объекта в едином change log образует один успешный результат.

**Успешный результат:** root и все его descendants отсутствуют в активном файловом дереве, а change log содержит достаточное отражение удаления всех затронутых объектов для последующей синхронизации клиентов.

**Инвариант процесса:** удаление поддерева является одной логической операцией. Частичный результат запрещён:

```text
удалена часть поддерева
+
часть поддерева осталась
→ недопустимо
```

Также недопустимо:

```text
объект удалён
+
change log не позволяет sync-клиенту узнать о его удалении
→ недопустимо
```

Итоговая модель:

```text
DELETE folder(root, knownVersion)

session valid
↓
root resolves without disclosure
↓
NON-ADMIN:
    DELETE действует на root + каждый descendant
ADMIN:
    permission bypass
↓
knownVersion(root) == currentVersion(root)
иначе conflict
↓
всё поддерево удаляется как одна логическая операция
+
change log достаточно отражает удаление всех затронутых объектов
↓
частичный результат запрещён
```

Требования пока не определяют технический способ физического удаления данных, формат записи deletion в change log или то, представляется ли удаление поддерева одной записью либо набором записей.

* SCOPE-INDEPENDENT-PERMISSIONS
* SCOPE-DELETION-TRACKING
* SCOPE-VERSIONING
* SCOPE-CONFLICT

## BP-FILE-TREE-GET-FILE-METADATA — прямое получение метаданных файла

Аутентифицированный пользователь напрямую получает метаданные существующего файла. Для non-admin этот отдельный прямой процесс определяется разрешением `GET_FILE_METADATA`; администратор обходит permission-проверку. `LIST_FOLDER` на родительскую папку для прямого запроса не требуется.

**Последовательность:**

1. **Прямой запрос метаданных.** Пользователь указывает конкретный файл, метаданные которого хочет получить.
2. **Проверка сессии.** Система проверяет, что пользовательская сессия существует, не истекла и остаётся действительной. Без действующей сессии метаданные не выдаются.
3. **Разрешение файла без раскрытия скрытой структуры.** Система определяет, может ли файл участвовать в операции в контексте полномочий пользователя. Для non-admin отрицательный результат не позволяет определить, отсутствует ли файл или существует, но скрыт/недоступен. Для администратора ограничение скрытия структуры не применяется.
4. **Проверка `GET_FILE_METADATA`.** Для non-admin проверяется разрешение `GET_FILE_METADATA` на прямое получение метаданных указанного файла. Для администратора проверка операцию не ограничивает. Если прямое получение метаданных не разрешено, метаданные не выдаются.
5. **Выдача метаданных.** Система возвращает метаданные указанного файла. Возвращаемые сведения не раскрывают недоступную пользователю родительскую структуру.

**Успешный результат:** пользователь напрямую получает метаданные конкретного файла без необходимости иметь `LIST_FOLDER` на его родительскую папку и без раскрытия недоступной родительской структуры.

Получение метаданных является read-only операцией:

```text
GET_FILE_METADATA
→ файл не изменяется
→ current version не изменяется
→ change log не изменяется
→ само по себе не считается просмотром содержимого файла
  или фактом ознакомления с ним
```

Конкретный состав метаданных на данном уровне не определяется.

## BP-FILE-CONTENT-UPLOAD — загрузка нового файла

Аутентифицированный пользователь создаёт новый файл непосредственно внутри выбранной родительской папки и передаёт его содержимое. Для non-admin требуется `UPLOAD` на родительскую папку; администратор обходит permission-проверку. Для больших файлов передача может продолжаться после прерывания, но незавершённая передача ещё не является успешно загруженным файлом.

**Последовательность:**

1. **Начало загрузки.** Пользователь указывает родительскую папку, имя нового файла и передаёт или начинает передавать содержимое нового файла.
2. **Проверка сессии.** Система проверяет, что пользовательская сессия существует, не истекла и остаётся действительной. Без действующей сессии передача не может быть успешно завершена созданием нового файла.
3. **Проверка родительской папки без раскрытия скрытой структуры.** Система определяет, может ли указанная родительская папка участвовать в операции. Для non-admin отрицательный результат не позволяет определить, отсутствует ли папка или существует, но скрыта/недоступна. Для администратора ограничение скрытия структуры не применяется.
4. **Проверка `UPLOAD`.** Для non-admin проверяется `UPLOAD` на создание нового файла в выбранной родительской папке. `LIST_FOLDER`, `CREATE_FOLDER`, `UPDATE`, `RENAME`, `MOVE`, `DELETE` и другие независимые permissions для самой загрузки нового файла не требуются и не заменяют `UPLOAD`. Для администратора permission check операцию не ограничивает.
5. **Передача содержимого.** Система принимает содержимое нового файла. Для больших файлов передача может быть resumable. Пока передача не завершена, новый файл не существует как завершённый активный элемент файлового дерева, ему не устанавливается current version, создание файла не попадает в change log и действие не считается успешной загрузкой в file audit.
6. **Повторная проверка перед завершением.** Перед успешным завершением система повторно подтверждает действительность пользовательской сессии, существование и допустимость родительской папки и, для non-admin, действующий `UPLOAD`. Изменение ACL или файлового дерева во время долгой передачи не должно позволять завершить upload на основании уже устаревшего разрешения.
7. **Проверка имени.** Полное имя нового файла, включая extension, если он присутствует, проверяется по `BR-FILE-TREE-UNIQUE-CHILD-NAME` против всех непосредственных дочерних элементов parent без учёта регистра. В проверку входят скрытые и недоступные siblings независимо от их типа. При конфликте новый файл не создаётся; для non-admin скрытый конфликт раскрывается только как «имя недоступно/занято» согласно `BR-FILE-TREE-HIDDEN-NAME-CONFLICT-DISCLOSURE`. `UPLOAD` не перезаписывает существующий объект с конфликтующим именем; изменение содержимого существующего файла относится к `UPDATE`.
8. **Завершение и фиксация.** Создание нового файла с полностью переданным содержимым, установка initial current version, применение ACL-наследования, запись создания в единый change log и audit-запись пользователя, успешно загрузившего файл, образуют единый успешный результат операции.

**Успешный результат:** новый файл существует как непосредственный дочерний элемент выбранной папки под незанятым именем, содержит полностью завершённое переданное содержимое, имеет current version, подчиняется действующим правилам ACL и наследования, его создание присутствует в change log, а file audit позволяет определить пользователя, успешно загрузившего файл.

**Инвариант resumable upload:** незавершённая передача может быть сохранена для последующего продолжения, но она не является успешно загруженным файлом:

```text
transfer incomplete
→ active file отсутствует
→ current version файла отсутствует
→ creation change log отсутствует
→ successful UPLOAD audit отсутствует
```

**Инвариант успешного завершения:** недопустимо состояние:

```text
файл считается успешно загруженным
+
нет завершённого содержимого
ИЛИ нет current version
ИЛИ нет соответствующего change log
ИЛИ нельзя определить uploader по audit
→ недопустимо
```

`UPLOAD` создаёт **новый** файл, поэтому caller-known version не требуется. Если объект с конфликтующим именем уже существует, операция не превращается в `UPDATE` и не перезаписывает его.

При проверке имени учитываются также скрытые siblings с той же case-insensitive семантикой полного имени. Единственная допустимая информация для non-admin при таком конфликте — выбранное имя недоступно; сам скрытый объект остаётся нераскрытым.

Сам факт успешной загрузки **не предоставляет загрузившему пользователю дополнительных разрешений** на новый файл. Разрешения определяются действующими правилами ACL и наследования.

Конкретный механизм resumable/multipart передачи, размер частей, идентификатор незавершённой передачи, срок её хранения и технический формат initial version, change-log записи и audit-записи на данном уровне не определяются.

* SCOPE-FILE-AUDIT

## BP-FILE-CONTENT-DOWNLOAD — скачивание исходного файла

Аутентифицированный пользователь получает исходное содержимое существующего файла. Для non-admin требуется отдельное разрешение `DOWNLOAD`; администратор обходит permission-проверку. Успешное скачивание фиксируется в file audit и одновременно считается просмотром с точки зрения определения факта ознакомления пользователя с файлом.

**Последовательность:**

1. **Запрос исходного файла.** Пользователь указывает файл, исходное содержимое которого хочет получить.
2. **Проверка сессии.** Система проверяет, что пользовательская сессия существует, не истекла и остаётся действительной. Без действующей сессии исходный файл и его исходные байты не выдаются.
3. **Проверка файла без раскрытия скрытой структуры.** Система определяет, может ли указанный файл участвовать в операции в контексте полномочий пользователя. Для non-admin отрицательный результат не позволяет определить, отсутствует ли файл или существует, но скрыт/недоступен. Для администратора ограничение скрытия структуры не применяется.
4. **Проверка `DOWNLOAD`.** Для non-admin проверяется отдельное разрешение `DOWNLOAD`. `VIEW`, `LIST_FOLDER`, `GET_FILE_METADATA` и другие независимые permissions для скачивания исходного файла не требуются и не заменяют `DOWNLOAD`. Наличие `VIEW` без `DOWNLOAD` не позволяет получить исходный файл или его исходные байты. Для администратора permission check операцию не ограничивает.
5. **Выдача исходного содержимого и аудит.** Если все проверки успешны, успешная выдача исходного содержимого и фиксация соответствующего скачивания в аудите образуют обязательный результат успешной операции. Аудит позволяет определить как минимум файл, пользователя, вид действия и время успешного скачивания. Успешное скачивание одновременно учитывается как просмотр при определении факта ознакомления. Если исходное содержимое не было успешно выдано, успешное скачивание не считается состоявшимся.

**Успешный результат:** пользователь получает исходное содержимое указанного файла, а audit позволяет определить, что этот пользователь успешно скачал файл и поэтому считается ознакомившимся с ним.

`DOWNLOAD` является read-only операцией:

```text
DOWNLOAD
→ содержимое файла не изменяется
→ current version не изменяется
→ change log не изменяется
→ caller-known version не требуется
```

Семантика разрешений и аудита:

```text
DOWNLOAD = разрешено
VIEW = запрещено
→ исходный файл может быть скачан,
  если остальные проверки успешны
→ успешное скачивание всё равно считается просмотром для audit/read-status
```

```text
VIEW = разрешено
DOWNLOAD = запрещено
→ исходный файл и его исходные байты не выдаются
→ просмотр относится к отдельному BP-FILE-CONTENT-VIEW
```

То есть следствие `DOWNLOAD ⇒ viewed` относится к факту ознакомления и аудиту, а не превращает `DOWNLOAD` в разрешение `VIEW` и не объединяет эти операции.

Требования на данном уровне не определяют транспорт скачивания, streaming/range semantics, технический формат выдачи файла или поведение частично прерванной передачи сверх правила, что успешным скачиванием считается только успешно завершённая выдача исходного содержимого.

**Связи:**

* UC-FILE-CONTENT-DOWNLOAD
* SCOPE-FILE-CONTENT
* SCOPE-INDEPENDENT-PERMISSIONS
* SCOPE-FILE-AUDIT
* SCOPE-HIDDEN-ANCESTORS
* SCOPE-ADMINISTRATION

## BP-FILE-CONTENT-UPDATE — изменение содержимого существующего файла

Аутентифицированный пользователь заменяет текущее содержимое существующего файла новым содержимым. Для non-admin требуется отдельное разрешение `UPDATE`; администратор обходит permission-проверку, но не проверку caller-known version. Для большого нового содержимого передача может продолжаться после прерывания; пока операция не завершена успешно, прежнее содержимое остаётся текущим.

**Последовательность:**

1. **Начало изменения.** Пользователь указывает изменяемый файл, известную ему версию файла и передаёт или начинает передавать новое содержимое.
2. **Проверка сессии.** Система проверяет, что пользовательская сессия существует, не истекла и остаётся действительной. Без действующей сессии новое содержимое не может стать текущим.
3. **Проверка файла без раскрытия скрытой структуры.** Система определяет, может ли файл участвовать в операции. Для non-admin отрицательный результат не позволяет определить, отсутствует ли файл или существует, но скрыт/недоступен. Для администратора ограничение скрытия структуры не применяется.
4. **Проверка `UPDATE`.** Для non-admin проверяется отдельное разрешение `UPDATE`. `VIEW`, `DOWNLOAD`, `UPLOAD`, `LIST_FOLDER`, `GET_FILE_METADATA` и другие независимые permissions не требуются и не заменяют `UPDATE`. Для администратора permission check операцию не ограничивает.
5. **Передача нового содержимого.** Система принимает новое содержимое. Большая передача может быть resumable. Пока передача не завершена, прежнее содержимое остаётся текущим, current version не меняется, change log не меняется и successful `UPDATE` audit не создаётся. Незавершённая передача сама по себе не считается просмотром файла.
6. **Повторная проверка и проверка версии.** Непосредственно перед применением нового содержимого система повторно проверяет действительность сессии, существование и доступность файла и, для non-admin, наличие `UPDATE`. Затем caller-known version сравнивается с текущей версией. При stale version операция отклоняется как conflict без автоматического разрешения: новое содержимое не становится текущим, версия не меняется, успешные change-log и audit записи не создаются. Проверка версии обязательна и для администратора.
7. **Применение и фиксация.** Если передача завершена и все проверки успешны, замена текущего содержимого, установка новой current version, запись изменения в единый change log и audit-запись пользователя, успешно изменившего файл, образуют единый успешный результат. Само изменение содержимого не считается просмотром или фактом ознакомления.

**Успешный результат:** новое содержимое является текущим содержимым того же файла, файл имеет новую current version, соответствующее изменение присутствует в change log, а audit позволяет определить пользователя, успешно изменившего файл.

**Инвариант незавершённой передачи:** 

```text
replacement transfer incomplete
→ прежнее содержимое остаётся current
→ current version не изменяется
→ change log не изменяется
→ successful UPDATE audit отсутствует
```

**Инвариант stale version:**

```text
caller-known version != current version
→ conflict
→ новое содержимое не применяется
→ current version не изменяется
→ successful change log отсутствует
→ successful UPDATE audit отсутствует
```

**Инвариант успешного завершения:** недопустимо состояние, в котором содержимое уже считается успешно изменённым, но отсутствует новая current version, соответствующая запись в change log или audit-запись успешного `UPDATE`.

Семантика независимых разрешений и аудита:

```text
UPDATE = разрешено
VIEW = запрещено
DOWNLOAD = запрещено
→ содержимое может быть изменено,
  если остальные проверки успешны
→ сам UPDATE не помечает пользователя как просмотревшего файл
```

Хранение и восстановление предыдущего содержимого как истории версий в Backend V1 не требуется. Требования на данном уровне не определяют механизм resumable/multipart передачи, размер частей, формат current version, change-log записи, audit-записи или технический способ адресации файла.

**Связи:**

* UC-FILE-CONTENT-UPDATE
* SCOPE-FILE-CONTENT
* SCOPE-INDEPENDENT-PERMISSIONS
* SCOPE-VERSIONING
* SCOPE-CONFLICT
* SCOPE-FILE-AUDIT
* SCOPE-CHANGE-LOG

## BP-FILE-CONTENT-VIEW — контролируемый просмотр содержимого файла

Аутентифицированный пользователь получает отдельное представление содержимого существующего файла для просмотра. Для non-admin требуется отдельное разрешение `VIEW`; администратор обходит permission-проверку. `VIEW` является самостоятельной операцией относительно `DOWNLOAD`: даже если у пользователя есть `DOWNLOAD`, через этот процесс исходный файл и его исходные байты не выдаются.

**Последовательность:**

1. **Запрос просмотра.** Пользователь указывает файл, содержимое которого хочет просмотреть.
2. **Проверка сессии.** Система проверяет, что пользовательская сессия существует, не истекла и остаётся действительной. Без действующей сессии representation не выдаётся.
3. **Проверка файла без раскрытия скрытой структуры.** Система определяет, может ли файл участвовать в операции. Для non-admin отрицательный результат не позволяет определить, отсутствует ли файл или существует, но скрыт/недоступен. Для администратора ограничение скрытия структуры не применяется.
4. **Проверка `VIEW`.** Для non-admin требуется отдельное разрешение `VIEW`. `DOWNLOAD`, `LIST_FOLDER`, `GET_FILE_METADATA` и другие независимые permissions не требуются и не заменяют его. `DOWNLOAD` без `VIEW` не разрешает controlled-view operation; исходный файл при наличии `DOWNLOAD` относится к отдельному процессу скачивания. Для администратора permission check операцию не ограничивает.
5. **Подготовка представления.** Система формирует или получает отдельное representation содержимого, пригодное для просмотра. Оно должно позволять ознакомиться с содержимым, но не является исходным файлом и не выдаёт его исходные байты. Конкретный формат representation и способ его формирования на этом уровне не определяются.
6. **Повторная проверка перед выдачей.** Непосредственно перед выдачей система повторно подтверждает действительность сессии, существование и доступность файла и, для non-admin, действующий `VIEW`. Если условие перестало выполняться, representation не выдаётся и successful `VIEW` audit не создаётся. Для администратора permission check не ограничивает операцию.
7. **Выдача representation и аудит.** Успешная выдача отдельного представления и фиксация соответствующего просмотра в audit образуют обязательный результат успешно завершённой операции. Audit позволяет определить как минимум файл, пользователя, вид действия и время. Именно успешная выдача representation считается просмотром; один запрос, разрешение файла или подготовка representation без успешной выдачи не считаются просмотром.

**Успешный результат:** пользователь получает controlled representation содержимого файла, исходный файл и original bytes через `VIEW` не выдаются, а audit позволяет определить, что пользователь успешно просмотрел файл.

Семантика разрешений:

```text
VIEW = разрешено
DOWNLOAD = запрещено
→ controlled representation выдаётся,
  если остальные проверки успешны
→ original bytes не выдаются
```

```text
VIEW = разрешено
DOWNLOAD = разрешено
→ VIEW всё равно выдаёт controlled representation
→ DOWNLOAD остаётся отдельной операцией
```

```text
VIEW = запрещено
DOWNLOAD = разрешено
→ controlled VIEW не выполняется
→ пользователь может отдельно скачать original через DOWNLOAD
→ успешный DOWNLOAD всё равно считается viewed для audit/read-status
```

`VIEW` является read-only операцией:

```text
VIEW
→ содержимое файла не изменяется
→ current version не изменяется
→ change log не изменяется
→ caller-known version не требуется
```

Подробный file audit остаётся доступен только администратору; сам факт `VIEW` не предоставляет пользователю право читать audit.

Controlled view **не является DRM**. Требование гарантирует, что сервер через `VIEW` не выдаёт исходный файл или его исходные байты, но не гарантирует невозможность скриншота, фотографирования экрана, копирования видимого текста или других действий пользователя после отображения representation.

Требования на этом уровне не определяют формат представления, преобразователи форматов, watermarking, URL/token semantics, streaming, caching или иные технические механизмы controlled view.

**Связи:**

* UC-FILE-CONTENT-VIEW
* SCOPE-CONTROLLED-VIEW
* SCOPE-INDEPENDENT-PERMISSIONS
* SCOPE-FILE-AUDIT
* SCOPE-HIDDEN-ANCESTORS
* SCOPE-ADMINISTRATION

## BP-ADMIN-MANAGE-ACCESS — административное управление доступом

Аутентифицированный администратор управляет назначением разрешений конкретному пользователю в отношении выбранной папки. Один процесс покрывает три AAG-сценария: `GRANT`, `CHANGE` и `REVOKE`. Обычный пользователь не может выполнять этот процесс.

**Последовательность:**

1. **Запрос изменения доступа.** Администратор указывает тип операции (`GRANT`, `CHANGE` или `REVOKE`), целевого пользователя и выбранную папку. Для `GRANT` и `CHANGE` также передаётся набор файловых разрешений.
2. **Проверка административной сессии.** Система проверяет действительность пользовательской сессии и наличие у текущей учётной записи глобальных административных полномочий. Без обоих условий ACL не изменяется.
3. **Проверка целевых объектов.** Система проверяет существование целевой учётной записи и выбранной папки. Администратор может управлять доступом к папке независимо от ACL и скрытия структуры. Если пользователь или папка не существуют, ACL не изменяется.
4. **Проверка типа изменения.** Для `GRANT` и `CHANGE` набор может содержать любую комбинацию файловых permissions из `SCOPE-INDEPENDENT-PERMISSIONS`, включая пустой набор. `GRANT` создаёт назначение для пары пользователь–папка и применяется, когда такого назначения на этой папке ещё нет. `CHANGE` меняет уже существующее назначение. `REVOKE` удаляет уже существующее назначение. `GRANT` не превращается автоматически в `CHANGE`, а `CHANGE`/`REVOKE` не создают отсутствующее назначение.
5. **Применение и change log.** Успешное изменение ACL и соответствующая запись об изменении прав доступа в едином change log образуют один успешный результат. При `GRANT` назначенный set начинает действовать на выбранной папке и наследоваться на descendants. При `CHANGE` прежний set заменяется новым и далее наследуется уже изменённый set. При `REVOKE` удаляется только соответствующее назначение. После любого изменения effective permissions пользователя вычисляются по `BR-ACL-EFFECTIVE-PERMISSIONS`; `REVOKE` не отменяет permissions, продолжающие предоставляться другими применимыми назначениями.

**Успешный результат:**

```text
GRANT
→ assignment существует
→ содержит указанный permission set
→ участвует в union effective permissions
→ действует на выбранной папке
→ наследуется на вложенные элементы
→ ACL change присутствует в change log

CHANGE
→ существующий assignment остаётся
→ его permission set заменён новым
→ union effective permissions пересчитывается
→ изменённое назначение наследуется
→ ACL change присутствует в change log

REVOKE
→ соответствующий assignment отсутствует
→ из union удалено только это основание
→ permissions из других применимых assignments сохраняются
→ ACL change присутствует в change log
```

Пустой permission set **не равен `REVOKE`**:

```text
assignment = {}
→ assignment существует
→ сам по себе не добавляет ни одной файловой операции
→ не отменяет inherited permissions
→ администратор может позднее выполнить CHANGE

REVOKE
→ assignment удалён
→ остальные применимые assignments продолжают действовать
```

Таким образом, после любой успешной операции управления ACL итоговый effective permission set определяется additive-union правилом `BR-ACL-EFFECTIVE-PERMISSIONS`.

Если `GRANT` вызван для уже существующего назначения либо `CHANGE`/`REVOKE` — для отсутствующего, ACL-состояние не изменяется и операция не подменяется другим типом изменения.

Не допускается состояние:

```text
ACL считается успешно изменённым
+
соответствующего изменения нет в change log
→ недопустимо
```

В Backend V1 назначать, изменять и отзывать доступ может только `ACTOR-ADMIN`.

**Связи:**

* UC-ADMIN-GRANT-ACCESS
* UC-ADMIN-CHANGE-ACCESS
* UC-ADMIN-REVOKE-ACCESS
* SCOPE-ACL
* SCOPE-ADMINISTRATION
* SCOPE-INDEPENDENT-PERMISSIONS
* SCOPE-CHANGE-LOG

## BP-ADMIN-VIEW-FILE-ACTIVITY — просмотр активности по файлу администратором

Процесс возвращает два семантически разных результата:

1. **audit history** — история зафиксированных действий всех пользователей, включая администраторов;
2. **current unviewed users** — только non-admin пользователи, которым файл сейчас доступен через ACL/effective permissions и которые ещё не имеют успешного `VIEW` или `DOWNLOAD`.

Глобальный административный доступ не используется при формировании current unviewed users.

**Последовательность:**

1. **Запрос отчёта.** Администратор указывает существующий файл, подробную информацию об активности которого хочет получить.
2. **Проверка административной сессии.** Система проверяет действительность пользовательской сессии и глобальные административные полномочия текущей учётной записи. Без обоих условий подробный file audit не выдаётся.
3. **Проверка файла.** Система проверяет существование выбранного файла. ACL и hidden-ancestor ограничения не препятствуют администратору работать с любым существующим файлом системы. Если файл не существует, отчёт не выдаётся.
4. **Получение audit history.** Система получает все зафиксированные успешные `UPLOAD`, `VIEW`, `DOWNLOAD` и `UPDATE` по выбранному файлу независимо от того, выполнялись они обычными пользователями или ADMIN. Для каждого действия известны как минимум пользователь, вид действия и время. Успешный `VIEW` считается ознакомлением; успешный `DOWNLOAD` также считается ознакомлением. `UPLOAD`, `UPDATE`, `LIST_FOLDER`, `GET_FILE_METADATA` и сам факт доступа ознакомлением не считаются.
5. **Определение non-admin пользователей с текущим доступом.** Система формирует кандидатов для current unviewed users только из пользователей без глобальных административных полномочий, которым файл доступен сейчас через действующие ACL и effective permissions. Effective set вычисляется по `BR-ACL-EFFECTIVE-PERMISSIONS`. ADMIN исключаются из этого множества независимо от их глобального доступа и независимо от наличия или отсутствия у них `VIEW`/`DOWNLOAD`. Исторический доступ, который уже отозван или изменён, сам по себе не включает non-admin пользователя в текущее множество.
6. **Определение не ознакомившихся.** Среди полученного non-admin множества система выбирает пользователей, для которых по выбранному файлу отсутствует успешный `VIEW` и отсутствует успешный `DOWNLOAD`. Наличие только `UPLOAD`, `UPDATE`, `LIST_FOLDER`, `GET_FILE_METADATA` или иных действий, не определённых как просмотр, не исключает пользователя из current unviewed users.
7. **Выдача отчёта.** Администратор получает audit history со всеми зафиксированными действиями, включая административные, и отдельный current unviewed users только с non-admin пользователями.

**Успешный результат:** администратор может определить по audit history:

- кто из всех пользователей, включая ADMIN, успешно загрузил файл;
- кто успешно просмотрел его через `VIEW`;
- кто успешно скачал original через `DOWNLOAD`;
- кто успешно изменял содержимое через `UPDATE`;
- когда происходило каждое такое действие.

Отдельно current unviewed users содержит только пользователей, удовлетворяющих одновременно условиям:

```text
user is NON-ADMIN
+
file currently accessible through ACL/effective permissions
+
successful VIEW absent
+
successful DOWNLOAD absent
→ current unviewed user
```

Для ADMIN действует другое правило:

```text
user is ADMIN
+
global administrative file access
+
successful VIEW/DOWNLOAD absent
→ NOT current unviewed user
```

При этом:

```text
ADMIN performs UPLOAD / VIEW / DOWNLOAD / UPDATE
→ action remains in audit history
```

Read-status для non-admin кандидатов сохраняет прежнюю семантику:

```text
successful VIEW
→ viewed = yes

successful DOWNLOAD
→ viewed = yes

UPLOAD only
→ viewed не следует

UPDATE only
→ viewed не следует

LIST_FOLDER only
→ viewed не следует

GET_FILE_METADATA only
→ viewed не следует

ACL/effective access only
→ viewed не следует
```

Audit history и current unviewed users имеют разные основания:

```text
audit history
→ совершённые успешные действия всех пользователей
→ включает ADMIN actions

current unviewed users
→ текущее ACL/effective-permission состояние
→ только NON-ADMIN
→ ADMIN global bypass не участвует
```

Операция является read-only:

```text
ADMIN VIEW FILE ACTIVITY
→ файл не изменяется
→ current version не изменяется
→ ACL не изменяется
→ change log не изменяется
→ caller-known version не требуется
```

Конкретные формат отчёта, сортировка, фильтрация и пагинация на уровне `RequirementsAnalysis` не определяются.

**Связи:**

* UC-ADMIN-VIEW-FILE-ACTIVITY
* SCOPE-ADMINISTRATION
* SCOPE-FILE-AUDIT
* SCOPE-ACL
* SCOPE-INDEPENDENT-PERMISSIONS
* BR-ACL-EFFECTIVE-PERMISSIONS

## BP-SYNC-GET-CHANGES — получение изменений для инкрементальной синхронизации

Аутентифицированный sync-клиент действует от имени пользователя, передаёт локально сохранённую позицию единого журнала и получает основанный на последующих изменениях sync-result, достаточный для приведения локального состояния к актуальному состоянию ресурсов, которые должны быть доступны этому пользователю с учётом его текущего административного статуса и ACL.

Сервер не хранит отдельный cursor клиента или устройства и не создаёт отдельный per-device change log.

**Последовательность:**

1. **Передача позиции.** Sync-клиент передаёт в рамках пользовательской сессии известную ему локально сохранённую позицию единого change log.
2. **Проверка сессии.** Система проверяет действительность пользовательской сессии и определяет пользователя, от имени которого действует клиент. Без действующей сессии sync-result не выдаётся.
3. **Проверка позиции.** Система проверяет, что переданная позиция может использоваться как граница инкрементального чтения. Если это невозможно, процесс не считается успешной инкрементальной синхронизацией и клиент не должен продвигать локальный cursor. Конкретные причины недопустимости позиции и recovery-механизм на этом уровне не определяются.
4. **Рассмотрение журнала после позиции.** Система рассматривает изменения глобального упорядоченного журнала строго после переданной позиции и в его порядке. Глобальный change log остаётся единым: отдельная серверная последовательность для клиента или устройства не создаётся.
5. **Применение disclosure rules.** Система учитывает текущий административный статус пользователя, ACL, `BR-ACL-EFFECTIVE-PERMISSIONS` и hidden-ancestor rules. Non-admin не получает данные о ресурсах, которые ему нельзя раскрывать. Для ADMIN global powers снимают ACL/hidden-ancestor ограничения.
6. **Отражение переходов состояния.** Результат должен быть достаточен для фактической конвергенции локального состояния. Он позволяет убрать удалённые ресурсы, ресурсы, к которым потерян доступ из-за ACL, и ресурсы, потерянные после `REVOKE_ADMIN`, если они не сохраняются через обычный ACL. При `GRANT_ADMIN` клиент должен иметь возможность получить актуальное состояние ресурсов, которые стали доступны глобально, даже если сами ресурсы после cursor не изменялись.
7. **Возврат результата и journal boundary.** Система возвращает упорядоченный sync-result и позицию глобального журнала, до которой он сформирован. Эта граница позволяет клиенту после успешной обработки продвинуть cursor также через серверные изменения, которые были рассмотрены, но не раскрыты пользователю.
8. **Продвижение локальной позиции.** Только после успешной обработки результата клиент заменяет свою локально сохранённую позицию на возвращённую границу. При неуспешной обработке прежняя позиция остаётся. Сервер cursor клиента или устройства не сохраняет.

**Успешный результат:** клиент получает безопасный инкрементальный результат, достаточный для приведения локального состояния к актуальной области ресурсов, доступных пользователю по его текущему административному статусу и применимым ACL.

Ключевая семантика фильтрации:

```text
global change log
→ единый для всей системы

NON-ADMIN sync result
→ не обязан содержать raw global entries
→ не раскрывает недоступные ресурсы
→ при этом позволяет продвинуть cursor через рассмотренную часть журнала
```

ACL transitions:

```text
ACL grant/change
→ новый existing subtree стал доступен
→ sync должен позволить получить его актуальное состояние
```

```text
ACL revoke/change
→ previously available subtree больше недоступен
→ sync должен позволить убрать его из локального состояния
```

Administrative-status transitions:

```text
GRANT_ADMIN
→ user gains global access
→ sync должен позволить получить актуальное состояние
  newly accessible resources
```

```text
REVOKE_ADMIN
→ global bypass removed
→ resources without remaining ACL access
  должны быть удалены из local state
```

Удаление также должно приводить к удалению локального состояния:

```text
server resource deleted
→ deletion отражено через sync
→ client может удалить local representation
```

Cursor хранится только клиентом:

```text
server
→ не хранит per-device cursor
→ не требует device registration для cursor

client
→ хранит last successfully processed position
→ передаёт её при следующем запросе
→ изменяет только после successful processing
```

Требования намеренно не определяют конкретное representation переходов ACL/admin-status, cursor encoding, batching, pagination, response limits или retention policy журнала.
